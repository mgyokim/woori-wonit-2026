## 1. 웹은 어떻게 동작하는가

### WWW의 출발점

곳곳의 컴퓨터에 저장되어 있는 정보를 인터넷을 통해 연결해, **언제 어디서건 누구라도 접근할 수 있게** 하는 방법을 고민하다 나온 것이 웹이다.

핵심은 이것이다. **정보의 소유권은 소유자에게 그대로 둔 채, 활용도만 극대화한다.**

### 웹의 세대

| 세대 | 특징 |
| --- | --- |
| 웹 1.0 | 문서 중심. 정적 사이트 |
| 웹 2.0 | JavaScript 출현. 페이지가 동적으로 나오기 시작 |
| 웹 3.0 | CGI(Common Gateway Interface) 등장. 웹 서버와 외부 프로그램이 정보를 주고받는 방법 · 규약이 생김 — 이 기술이 발전해 **지금의 백엔드**가 됨 |
| 웹 4.0 | HTML5 표준이 나오기 시작 |

**웹 4.0에서 달라진 것**

- 어도비 플래시 플레이어 대신, 이미지 · 동영상 · 음성을 HTML에서 **직접 연결**할 수 있게 됨
- `<audio>` `<video>` 태그로 웹에서 동영상 · 음성 데이터를 바로 보여줌
- 사용자 **접근성**을 중시하는 방향으로 HTML이 업그레이드됨
- JavaScript가 **표준 언어**로 지정됨

> 이 세대 구분은 강의에서 정리한 기준이다. 바깥에서 흔히 말하는 "웹 3.0(시맨틱 웹 · 블록체인)"과는 다른 구분이라, 검색할 때 헷갈리지 않도록 기억해 둘 것.

### 웹 서버와 웹 클라이언트

인터넷이 동작하려면 **최소 2대의 컴퓨터**가 필요하다.

| | 하는 일 |
| --- | --- |
| **웹 서버** | 데이터 저장 · 관리 / 웹 클라이언트의 요청을 받아 웹 문서 전송 / 웹 서버로 작동하도록 하는 소프트웨어 실행 |
| **웹 클라이언트** | 사용자 인터페이스 담당 / 웹 서버에 웹 문서를 요청하고, 받아와서 사용자에게 출력 |

![교육장 네트워크 구성 및 정보](img.png)

우리 교육장의 네트워크 구성 도식이다.

### 웹 표준과 크로스브라우징

웹 표준은 **W3C의 권고안**에서 나온 기술들이다.

이 표준 기술을 기준으로 브라우저(크롬 · 사파리 · 파이어폭스)가 만들어지는데, 만드는 업체마다

- 표준 기술을 **해석하는 차이**
- **새로운 기술 삽입**

이 있어서 조금씩 다르게 구동되는 브라우저가 생긴다. **웹 표준을 지키는 이유가 곧 크로스브라우징**이다.

## 2. 웹의 3요소

| 요소 | 역할 | 비유 |
| --- | --- | --- |
| **HTML** | 구조 — 버튼, 입력창, 박스 | 뼈대 |
| **CSS** | 스타일 — 색상, 간격, 정렬 | 옷 |
| **JavaScript** | 동작 — 클릭 시 데이터 전송, 팝업 | 근육 |

### HTML 문서의 뼈대

AI가 짜준 코드를 **어디에 붙여넣어야 하는지** 알기 위해 반드시 알아야 하는 구조다.

```html
<!DOCTYPE html>
<html lang="ko">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>나의 AI 서비스</title>
    <!-- 여기에 외부 CSS 링크 -->
  </head>
  <body>
    <!-- 여기에 사용자에게 보이는 화면(UI) -->
    <!-- 여기에 JavaScript 태그 (body 맨 끝 권장) -->
  </body>
</html>
```

- `lang="ko"` — 문서 언어 선언. **스크린리더 발음**과 브라우저 번역 판단의 기준
- `charset` — 없으면 브라우저가 인코딩을 추측해서 **한글이 깨진다**. `head` 최상단에 둘 것

### DOM (Document Object Model)

- 브라우저는 HTML 문서를 읽어 **트리 구조(DOM 트리)** 로 만든다
- JavaScript로 트리의 특정 요소(예: `id="chat-box"`)를 찾아 내용을 바꾸거나 새로 추가한다
- 직접 복잡한 DOM 조작을 쓰기보다, AI에게 **"id가 chat-box인 곳에 채팅 메시지를 추가하는 함수를 짜줘"** 라고 요구한다

## 3. HTML 기초

### 문서 작성 규칙

- 태그(TAG)로 이루어진다
- **부모와 자식** 요소가 있다
- 기본적으로 태그들은 **계층적인 구조**를 같이 표현한다

### Emmet

약어로 태그 구조를 한 번에 펼치는 기능. `div>ol>li` 를 치고 `Tab`.

- 문법 참고 : https://docs.emmet.io/abbreviations/syntax/

### 시맨틱 태그 — 계좌 카드 만들기

CSS 없이 **구조만** 만들면서, 태그를 왜 골랐는지 한 줄씩 남겼다.

| 태그 | 고른 이유 |
| --- | --- |
| `<article>` | 카드 한 장이 **그 자체로 완결된** 독립 콘텐츠라서. 다른 화면에 그대로 옮겨도 말이 된다 |
| `<header>` | 카드의 머리말. "어느 은행 계좌인지" 식별하는 정보를 묶는 자리 |
| `<h2>` | 페이지 제목(`h1`) **아래 계층**이므로 `h1`이 아니다 |
| `<dl>` `<dt>` `<dd>` | "이름 - 값" 쌍이 반복되는 구조라 정의 목록이 정확하다. `table`은 행과 열이 있는 **2차원** 데이터용 |
| `<data value="1523000">` | 사람이 읽는 `"1,523,000원"` 과 기계가 읽는 **원 단위 정수**를 같이 담는다 |
| `<footer>` | 본문에 딸린 보조 영역. 이 카드에 대한 행동 버튼을 모은다 |
| `<button type="button">` | 다른 문서로 가는 게 아니라 **동작**을 일으키므로 `a`가 아니다. `type`을 생략하면 `form` 안에서 **submit으로 동작해 폼이 전송되는 사고**가 난다 |

`<div>` 는 의미가 없는 상자다. **쓸 수 있는 곳엔 시맨틱 태그**를 쓰는 것이 웹 접근성의 출발점이다.

### block vs inline

영역을 위한 태그는 두 종류다.

| | block | inline |
| --- | --- | --- |
| 차지하는 영역 | 위치한 **줄 전체** | 자기가 **위치한 만큼만** |
| 태그 | `h` `p` `ol` `li` `ul` `div` | `a` `img` `span` |
| 쌓이는 방향 | 수직 | 수평 |
| `width` / `height` | 지정 가능 | **지정 불가** — 바로 옆 요소에 영향을 주기 때문 |

### 폼과 input

`type` 에 따라 입력 UI가 완전히 달라진다.

```html
<input type="text" size="5" name="text">
<input type="password" name="password" required>
<input type="date" name="date" min="2020-01-01" max="2020-12-31">
<input type="color">
<input type="number" name="num" min="0" max="1000">
<input type="range" name="point" min="0" max="100">
<input type="tel" name="phone" pattern="[0-9]{3}-[0-9]{4}-[0-9]{4}">
```

- **라디오** — `name` 으로 묶어서 하나의 단위를 만들고, 그 중 하나만 선택된다
- `value` 에는 실제로 백엔드/JS에서 쓸 값을 적는다. **영어로, 띄어쓰기 없이**
- `<form>` 의 `submit` 은 폼을 통째로 전달, `reset` 은 통째로 초기화
- 쿼리스트링 — `?` 뒤에 `키=값&키=값` (`?name=김민교&affiliation=FIS-WONIT`)

### 폼 데이터 다루기

`method` 를 `get` → `post` 로 바꿔가며 전송되는 값을 관찰했다. (`post` 는 개발자도구 → Network → Payload)

**전송되는 값의 규칙 세 가지**

- 한글이 `%EA%B9%80` 처럼 바뀐다 → **URL 인코딩**
- 체크박스 여러 개는 `avail_language=HTML&avail_language=CSS` 처럼 **같은 이름이 반복**된다
- **체크 안 한 라디오 · 체크박스는 아예 안 들어간다** (빈 텍스트 칸은 `sex=` 처럼 들어간다)

**값을 꺼내는 방법이 종류마다 다르다**

| 종류 | 꺼내는 법 |
| --- | --- |
| text, date, color, range, tel | `.value` |
| 체크박스 하나 | `.checked` (true / false) |
| 라디오 묶음 | `.value` — 선택된 것의 값 |
| 체크박스 묶음 | 반복문으로 `.checked` 인 것만 모은다 |
| multiple select | `.selectedOptions` |

> 같은 `name` 이 **하나뿐이면 목록이 아니라 요소 하나**가 온다. 이 예외 처리가 빠지면 체크박스를 하나로 줄였을 때 코드가 깨진다.

## 4. AI로 페이지 만들기

프론트엔드를 **'직접 짜는 곳'이 아니라 'AI가 짜준 코드를 조립하는 곳'** 으로 보는 것이 오늘의 관점이다.
그러려면 요구를 정확히 적어야 한다.

**나쁜 예** — "채팅 화면 만들어줘"
→ AI가 임의의 프레임워크나 복잡한 CSS로 코드를 던진다. 유지보수 불가.

**좋은 예**

> "MUI를 사용해서 **단일 HTML 파일**로 채팅 화면을 만들어줘. 화면 중앙에 채팅창이 있고, 아래에 입력창과 전송 버튼이 있어야 해. CSS는 MUI 클래스만 최대한 사용하고 최소한의 custom CSS만 `<style>` 태그에 넣어줘."

### 정확도를 올리는 세 가지

| | 방법 | 방지 효과 |
| --- | --- | --- |
| **A** | **프레임워크 명시** — "MUI 최신버전, CDN 포함 단일 HTML 파일로" | 구버전 코드, 알 수 없는 CSS, React/Vue 코드 지양 |
| **B** | **구조와 디자인 묘사** — "상단에 파란 배경 네비게이션 바(로고 + 로그인 버튼), 중앙에 Card 형태 폼" | 원하는 레이아웃과 동떨어진 결과물 방지 |
| **C** | **class 우선, 커스텀 CSS 최소화** — "기본 utility 클래스를 쓰고 `<style>` 안의 커스텀 CSS는 최소화" | 코드가 길어져 나중에 수정하기 어려워지는 현상 방지 |

## 5. 실습

### 실습 ① AI에게 구조만 시켜보기

아직 CSS를 배우지 않은 상태라 **구조만** 요청했다.

```
너는 금융권 프론트엔드 개발자다.
은행 앱의 "계좌 카드" 화면 구조를 HTML만으로 만들어 줘.

[표시 내용]
- 은행명 (제목) / 계좌번호 (마스킹된 텍스트) / 잔액
- 버튼 두 개: "이체", "상세"

[제약]
- CSS는 쓰지 말고 HTML 구조만.
- 시맨틱 태그를 쓸 수 있는 곳은 시맨틱 태그로.
- 각 태그 옆에 왜 이 태그를 골랐는지 한 줄 주석.
```

결과를 받은 뒤 반드시 되물을 것 — **"여기서 `<div>` 대신 시맨틱 태그를 쓸 수 있는 곳이 있어?"**

이 되물음에서 `<div>` 로 감싸져 있던 곳이 `<article>` `<dl>` `<footer>` 로 바뀌었다.
**첫 답을 최종본으로 받지 않는 것**이 핵심이다.

### 실습 ② 나의 포트폴리오 페이지 (진행 예정)

- `index.html` — 1일차에 만든 GitHub 자기소개 마크다운을 넘겨 HTML로 변환 요청
- `keyword.html` — 나를 설명하는 키워드 3가지를 각각 박스 컨테이너로
  - 즐겨보는 콘텐츠 / 취미 / 외출할 때 가방에 꼭 챙기는 물품

**완성 기준**

- 시맨틱 태그로 `header` / `main` / `footer` 완성
- `header` 에 두 페이지를 오가는 **navigation bar**
- 의미 없는 `<div>` 를 최소한으로, 쓸 수 있는 곳엔 시맨틱 태그로 **웹 접근성 준수**

## 회고

**Keep** — 태그마다 "왜 이걸 골랐는지" 주석을 한 줄씩 남긴 것. `button` 의 `type` 을 생략하면 폼이
전송된다는 건 주석을 쓰려고 근거를 찾다가 알게 됐다. 설명을 적으려면 먼저 이해해야 한다.

**Problem** — AI가 준 첫 구조는 대부분 `<div>` 였다. 그대로 받았으면 "동작은 하지만 의미가 없는"
HTML이 남았을 것이다. 되물었을 때야 시맨틱 태그로 바뀌었는데, **되물을 줄 몰랐으면 몰랐을 문제**다.

**Try** — 요청할 때 제약(프레임워크 · 단일 파일 · 커스텀 CSS 최소화)을 처음부터 적어 본다.
오늘은 결과를 받고 고치는 쪽이었는데, 제약을 먼저 주는 편이 왕복이 적을 것 같다.

> HTML을 배우는 이유가 "직접 다 짜기 위해서"가 아니라 **AI가 준 코드를 읽고 판단하기 위해서**로
> 바뀌었다. `<div>` 를 `<article>` 로 바꾸라고 말할 수 있으려면, 그 차이를 아는 사람이어야 한다.
