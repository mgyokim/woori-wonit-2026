# 오전 — 정규교과 · JavaScript 참조 자료형

기본 자료형이 끝나고 배열 · 객체 · Map 으로 넘어갔다. 실습 파일 하나를 계속 키워가는 방식이라,
**새로 배우는 시간만큼 쌓인 코드를 정리하는 데** 시간을 썼다.

## 배열 — `splice` 하나가 삽입 · 삭제 · 교체를 다 한다

넣고 빼는 건 **어느 쪽 끝이냐**로 묶으면 외워진다.

| | 넣기 | 빼기 |
| --- | --- | --- |
| 맨 뒤 | `push()` | `pop()` |
| 맨 앞 | `unshift()` | `shift()` |
| 중간 | `splice(시작, 삭제개수, 넣을값...)` | |

삭제 개수를 `0` 으로 주면 순수 삽입, `1` 로 주면서 값을 넘기면 교체다.
넣을 값은 여러 개 가능해서 `splice(1, 1, 'bee', 'betray')` 는 **하나 빼고 둘을 넣어** 길이가 늘어난다.

## `sort()` 는 크기가 아니라 **부호**만 본다

그냥 `sort()` 를 쓰면 원소를 **문자열로 바꿔서** 비교한다. `[10, 9, 1]` 이 `[1, 10, 9]` 가 된다 —
`'1'` 과 `'9'` 의 첫 글자에서 승부가 나기 때문이다.

숫자로 정렬하려면 비교함수를 넘겨야 하는데, **`sort` 는 반환값의 부호만 쓴다.**

- 음수 → `a` 를 앞으로 · `0` → 그대로 · 양수 → `b` 를 앞으로

크기는 안 본다. `-1` 이든 `-565` 든 똑같이 "a 가 앞"이다.
그래서 `a - b` 는 **작은 값이 앞** = 오름차순, `b - a` 는 내림차순.
**왜 하필 뺄셈인가**가 여기서 풀렸다 — 뺄셈이 크기 비교를 **부호 하나로 압축**해주기 때문이다.

## Map 과 Object 는 key 를 다르게 저장한다

같은 숫자를 key 로 넣어도 결과가 정반대다.

| | 숫자 `2` 를 key 로 넣으면 | 꺼낼 때 |
| --- | --- | --- |
| **Object** | **문자열 `'2'`** 로 바꿔 저장 | `obj[2]` 도 `obj['2']` 도 됨 |
| **Map** | 숫자 `2` **그대로** | `get(2)` → 값, `get('2')` → **`undefined`** |

`Object.keys()` 를 찍으면 `[ '2', '가', '나' ]` 로 숫자가 **따옴표에 싸여** 나온다.
불리언 `true` 를 key 로 넣어도 `'true'` 가 된다 — **일반 객체의 key 는 무조건 문자열**이다.

그리고 Object 는 **숫자처럼 생긴 key 를 앞으로 당긴다.**
`{ '나': 1, 2: 2, '가': 3 }` 의 key 순서가 `[ '2', '나', '가' ]` — 넣은 순서가 아니다.
"key 의 순서는 보장되지 않는다"가 이런 뜻이었다.

## 에러 없이 사라지는 것들 — 오늘만 네 번

- **Map 에 `map['가'] = '가위'`** 로 직접 넣기 → **Map 요소가 안 된다.** `Map(3)` 인데 항목은 4개로 보이고,
  `size` 에 안 세어지고 `get()` 으로도 못 꺼내고 `for...of` 로도 안 나온다.
  출력에서 **`=>` 로 찍히면 Map 요소, `:` 로 찍히면 그냥 객체 속성**이다.
- **`JSON.stringify`** → `undefined` 와 함수가 **경고 없이 사라진다.**
  `{ a: 1, b: undefined, c: function(){} }` → `{"a":1}`
- **`NaN` 섞인 `sort`** → `NaN` 은 음수도 0도 양수도 아니라 판정 자체가 안 돼 정렬이 조용히 깨진다.
- **`default` 없는 `switch`** (Day 4) → 아무것도 출력 안 된다.

> **네 번째다.** Day 2 버그 5개 중 4개, Day 4의 `switch`, Day 5의 `0 < age`, 그리고 오늘.
> **"콘솔이 조용하면 정상"이라는 감각을 버려야 한다.**

## `JSON.parse` 는 새 객체를 만든다

```js
back === dict   // false
```

값은 똑같은데 `false` 다. 참조 자료형의 `===` 는 **값이 아니라 주소**를 비교하기 때문이다.
뒤집으면 이게 **객체를 깊게 복사하는 가장 간단한 방법**이기도 하다.

## 정리하면서 배운 것 — 이름이 거짓말하면 주석도 못 고친다

파일이 500줄을 넘어가면서 이름이 감당이 안 됐다. `array1` `array2` `array3` `array10`,
`dict` `dict2` `dict3`, `hello1`~`hello6`. **번호는 "몇 번째로 만들었나"만 말하고, 뭘 담았는지는 말하지 않는다.**

제일 위험했던 건 이 셋이다.

```js
dict2_data / dict_data2 / dict_data3   // 숫자 '2' 의 위치만 다르다
```

**오타를 내도 눈으로 못 잡는다.** 담은 내용으로 바꾸니 주석이 필요 없어졌다.

```js
wordByDot     = wordDict.가       // 점 표기법
wordByBracket = wordDict['가']    // 대괄호
```

`hello3` 는 **인사를 안 하고** 배열을 이어붙여서 `joinNames` 가 됐고,
`hello4/5/6` 은 `greetByAnonymous` / `greetByArrow` / `greetByArrowShort` 로 바꿨다 —
**세 함수가 결과는 같고 문법만 다르다**는 게 이름만 봐도 보인다.

> 이름을 바꾼 뒤 **실행 결과를 리네임 전과 대조**했다. 새 이름을 옛 이름으로 되돌려 비교했더니
> 완전히 같았다. "동작은 안 바꿨다"를 말이 아니라 **확인으로** 남길 수 있었다.

# 오후 ② — 개발 프로젝트 사업과 IT영업

> 우리FIS IT영업부 **인재욱 팀장** · 17:00~18:00

## 제목만 보고 오해했다

"IT영업"이라길래 발주처 만나고 인맥 쌓는 이야기인 줄 알았다.
실제로는 **IT 사업이 어떻게 굴러가는지에 대한 지도**였고, 강사도 첫 장에서 그 오해를 먼저 깼다.

> **IT영업은 "파는 사람"이 아니라 "사업을 성립시키는 사람"에 가깝다.**

고객의 사업 계획을 **함께 설계**하고, 기술·인력·기간을 **원가로 환산**하고,
조건과 리스크를 **문서로 방어**하고, 끝날 때까지 범위·일정·수익을 **관리**한다.
**어느 직무로 가든 이 지도 위에서 일하게 된다**는 말이 남았다.

## 여섯 단계 지도

```
발굴 · 기획 → 제안 · 입찰 → 계약 → 수행 → 이행 · 안정화 → 운영 · 유지보수
  1~6개월      2~8주      2~6주  6~30개월    1~3개월          수년
```

앞 세 단계는 **발주처가 주도**하고 뒤 세 단계는 **수행사가 주도**한다.

**돈과 조건은 3단계(계약)에서 정해지지만, 실제 손익은 4단계(수행)에서 갈린다.**
그래서 영업이 계약 후에 손을 떼지 않는다. 사례로 든 12개월짜리 사업에서도
**중간에 생긴 변경 3건을 어떻게 처리했느냐가 손익을 갈랐다**고 했다.

## 대가는 흥정이 아니라 계산이다

가격을 부르는 게 아니라 **공인된 기준으로 산정**한다. 소프트웨어산업협회 가이드가 사실상 표준이다.

| 방식 | 어떻게 | 어디에 |
| --- | --- | --- |
| **투입공수** | 몇 명 × 몇 개월 × 등급별 단가 | 운영 · 유지보수 · 상주 개발 |
| **기능점수(FP)** | 만들 기능의 양을 점수로 환산 | 신규 구축 · 차세대 |
| **고정가 · 실비정산** | 총액 확정 또는 실비 정산 | 소규모 · 범위 불확실 |

**원가가 인건비만이 아니라는 게 제일 놀라웠다.** 직접인건비에 제경비와 기술료가 붙어서,
**인건비 100 짜리 일이 고객 청구액으로는 약 2.8배**가 된다.
"개발자 한 명 월 얼마"라고만 생각하던 게 완전히 깨졌다.

## 계약 — 가장 자주 다투는 건 가격이 아니라 **범위**

> *"알아서 잘"* 이 계약서에 들어가는 순간 분쟁이 예약된다.

그래서 문서로 못박는 것들 — **과업 범위**(어디까지가 계약이고 어디부터 추가인가),
**추가 과업 절차**(늘면 대가는 어떻게 되는가), **검수 기준**(무엇을 충족해야 "완료"인가),
지체상금 · 하자담보 · 지식재산권 · 책임 한도.

**계약서는 잘 굴러갈 때는 아무도 안 보지만, 문제가 생기는 순간 유일한 근거**가 된다는 말이 남았다.

## 도급 · 위수탁 · 파견 — 남 얘기가 아니다

**같은 사람이 같은 자리에서 일해도 계약 형태에 따라 지휘·명령권과 책임이 완전히 달라진다.**

| | 무엇을 약속 | 지휘·명령 |
| --- | --- | --- |
| **도급** | 일의 완성 | 수행사가 자기 인력을 직접 |
| **위수탁** | 업무 처리 위탁 | 위탁 범위 내에서 수탁사가 |
| **근로자파견** | 인력을 보내 사용 | 사용사업주가 직접 |

도급으로 계약해놓고 고객사가 우리 직원에게 직접 지시하면 **위장도급(불법파견)** 이 될 수 있다.
그래서 계약서와 현장 운영 방식을 일치시키는 게 IT영업의 중요한 책무라고 했다.

**취업 후 내 계약이 어떤 형태인지와 직결되는 이야기**라 따로 적어둔다.
면접 준비할 때 **계열사 구조를 파악해두라**는 조언도 함께 받았다.

## 사업이 어긋나는 다섯 가지 — 네 개가 기술이 아니다

1. **범위가 흐릿하다**
2. 요구사항이 계속 는다 (스코프 크립)
3. 의사결정이 늦다
4. 소통 창구가 여러 개다
5. **검증을 마지막에 몰아 한다**

**5번만 기술 문제**고 나머지는 전부 합의와 소통이다.

> **오전과 여기가 이어진다.** 오늘 오전에 내가 고친 것도 문법 오류가 아니었다 —
> `hello3` 는 인사를 안 하면서 이름은 인사라고 했고, 주석은 `.size()` 라면서 코드는 `keys()` 를 불렀다.
> **이름과 주석은 "이 코드가 무엇을 하기로 했는지"에 대한 합의**인데, 그 합의가 코드와 달랐다.
> 계약서에서 "범위"가 흐릿한 것과 같은 종류의 문제다.

> 그리고 **5번**은 Day 2 · 4 · 5 에서 계속 나온 이야기다.
> 경계값을 안 넣어보고 넘어가면 나중에 훨씬 비싸게 찾는다.
