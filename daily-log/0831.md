## 오늘의 핵심 3가지

**1. 입력창에서 받은 값은 언제나 문자열이다.**
`"10000" + 500` 은 `10500` 이 아니라 **`"10000500"`** 이다. 숫자처럼 생겼다고 숫자가 아니다.
금액을 계산하기 전에는 반드시 `Number()` 로 바꾼다. 그래서 `==` 가 아니라 **`===`** 를 쓴다 —
`"10000" == 10000` 은 `true` 지만 `"10000" === 10000` 은 `false` 다.
헷갈리면 `typeof` 로 지금 값이 뭔지 먼저 확인.

> **Day 3와 이어진다.** 어제 폼에서 `.value` 로 꺼낸 값이 바로 이 문자열이다.
> 그때는 "값이 나온다"까지만 봤는데, 그 값으로 계산하면 사고가 난다는 게 오늘 이어졌다.

**2. `>` 와 `>=` 는 한 글자 차이지만 은행에서는 사고다.**
잔액 500,000원에 이체 500,000원이면 `amount > balance` 는 **거짓** — 전액 이체가 통과한다.
의도가 "잔액을 넘으면 막는다"인지 "잔액을 다 쓰면 막는다"인지에 따라 부호가 달라진다.
**경계값(같을 때)을 직접 넣어보지 않으면 이 차이는 안 보인다.**

**3. 이벤트 핸들러를 만든 것과 등록한 것은 다르다.**
함수를 만들어놓고 `onclick` 에 안 적으면 핸들러는 있지만 **등록이 안 된 상태**다.
브라우저에게 "이 사건이 나면 이걸 불러줘"라고 위임해야 비로소 동작한다.

> **Day 2와 이어진다.** 버그 1번이 `addEventListener("click", handleDeposit())` 였다.
> 괄호 때문에 즉시 실행되고 반환값 `undefined` 가 등록됐던 것 — **등록이 실패한 상태**였다.
> 그때는 "괄호를 빼야 한다"로 외웠는데, 오늘 등록이라는 개념을 알고 나니 왜인지가 설명된다.

## 헷갈렸던 것

### JS는 인터프리터 언어인데 컴파일을 한다?

강의에서 언어를 인터프리터 / 컴파일 둘로 나눴는데, 정작 JS 엔진의 동작은
**파싱 → 컴파일 → 실행** 이었다. 모순처럼 보였다.

정리하면 — **분류는 "실행 전에 통째로 번역해두느냐"** 를 말하는 것이고,
JS는 미리 번역된 결과물을 배포하지 않는다. 엔진이 **실행하는 시점에** 읽고 기계어로 바꾼다.
그래서 개발자 입장에서는 인터프리터처럼 쓰고(고치면 바로 반영), 속도는 컴파일된 코드로 낸다.

### `null` 의 타입이 `object` 로 찍힌다

`typeof null` 은 `"object"` 다. 값이 없다는 뜻인데 객체라고 나온다.
**JavaScript 자체의 버그**인데 고치면 기존 코드가 깨져서 그대로 유지되고 있다.

- **`null`** — 값이 없다고 **내가 정한** 상태. 빈 자리는 웬만하면 `null` 로 채운다
- **`undefined`** — 자바스크립트가 돌려주는 상태. 값을 대입 안 한 변수, `return` 없는 함수의 결과,
  존재하지 않는 속성을 가리킬 때

### 변수는 `const` 부터

`var` 는 여러 사람이 작업할 때 권장되지 않는다. **일단 전부 `const` 로 만들고,
바꿔야 하는 것만 `let` 으로 바꾸는** 순서를 권장받았다. 잔액은 `let`, 수수료율은 `const`.

실습에서 `var menu` 를 두 번 선언했는데 **에러가 안 났다.** `let` 이었으면
`SyntaxError: Identifier 'menu' has already been declared` 로 바로 죽는다.
`var` 는 같은 이름을 다시 선언해도 **조용히 덮어쓴다** — 권장하지 않는 이유가 이것이다.

### `switch` 에 `default` 가 없으면 조용히 아무 일도 안 일어난다

메뉴 분기 실습을 네 방법(`switch` × 2, `if` + `includes()`, 삼항연산자)으로 짜봤다.
첫 `switch` 에는 `default` 를 안 넣었는데, 값이 `case` 셋 중 하나가 아니면
**에러도 없고 출력도 없다.** `case` 를 연달아 쓰면(fallthrough) 여러 값을 한 블록으로 묶고
`default` 로 나머지를 받을 수 있다.

> **또 같은 유형이다.** Day 2 버그 5개 중 4개가 "에러는 없는데 결과가 이상한" 것이었다.
> 조건에 안 걸려서 조용히 넘어가는 코드는 콘솔이 알려주지 않는다.

## 실습 — 이체 가능 여부 판정

조건문을 함수로 묶어 "이체 가능한가"를 판정한다. 함수는 자판기다 —
재료(매개변수)를 넣으면 정해진 규칙대로 결과(반환값)가 나온다.

```js
function canTransfer(balance, amount, limit) {
  if (amount > balance) return false;   // 잔액 부족
  if (amount > limit)   return false;   // 한도 초과
  return true;
}
```

**조건의 순서가 사용자에게 보이는 메시지를 바꾼다.** 잔액도 부족하고 한도도 넘었을 때,
먼저 검사한 쪽이 이유로 표시된다. 어느 쪽을 먼저 알려주는 게 맞는지는 기술이 아니라 **판단**이다.

`return` 을 여러 번 쓰면 조건에 걸리는 즉시 빠져나온다. 하나로 합칠 수도 있지만
**조건이 늘어날 때 읽기 어려워진다.**

**AI를 세 역할로 나눠 썼다** — 조건 순서가 왜 그런지 물을 때는 *설명자*,
판정 로직 첫 버전을 받을 때는 *초안 작성자*, 빠진 조건이 없는지 볼 때는 *리뷰어*.
받은 코드는 한 줄씩 읽으며 주석을 직접 달았다.

## JavaScript가 못 하는 일

브라우저 위에서 돌기 때문에 **일부러 막아둔 것들**이 있다.

- 하드디스크의 임의 파일을 읽거나 쓸 수 없다 — 사용자가 **직접 끌어다 놓거나 `input` 으로 고를 때만**
- 카메라 · 마이크는 사용자가 **명시적으로 허락할 때만**
- 다른 도메인 · 프로토콜 · 포트에서 온 스크립트에 접근할 수 없다 → **동일 출처 정책(Same Origin Policy)**

> 금융 서비스를 만들 언어라서 이 제약이 그냥 불편함이 아니라 **설계된 안전장치**로 읽힌다.
