## 오전 — 정규교과 · JavaScript

Day 4에서 시작한 [JavaScript 첫걸음] 자료를 이어서 진행했다.
조건문을 **직접 짜보는** 쪽에 시간을 썼고, 그 과정에서 어제 정리한 내용이 실제로 걸렸다.

### 조건문에서 걸린 것 3가지

**1. 부등호 방향을 반대로 써도 에러가 안 난다.**

나이 분기 실습에서 "0살 미만은 막는다"를 이렇게 썼다.

```js
if (0 < age) {                                  // 의도: age < 0
  console.log("나이가 0보다 작을 수 없습니다.")
} else if (age < 13) { ... }
```

`0 < age` 는 **"age가 0보다 크다"** 다. 그래서 20을 넣으면 첫 줄에 걸려
`"나이가 0보다 작을 수 없습니다."` 가 나오고, 어린이 · 미성년자 · 성인 분기는 **한 번도 실행되지 않는다.**
반대로 -5를 넣으면 조건이 거짓이라 `age < 13` 으로 내려가 **"어린이"** 가 나온다. 정확히 뒤집힌 결과다.

문법은 완전히 정상이라 `node --check` 도 통과한다. **콘솔이 알려주지 않는 종류의 버그**다.
`0 < age` 와 `age < 0` 은 사람 눈에 둘 다 "0과 age를 비교"로 읽히는 게 함정이다.
그래서 **비교는 항상 `변수 < 값` 순서로 쓰기**로 정했다 — 읽는 순서와 뜻이 같아진다.

> **Day 4 · Day 2와 같은 유형이다.** Day 2 버그 5개 중 4개, Day 4의 `default` 없는 `switch`,
> 그리고 오늘이 전부 **"에러는 없는데 결과가 이상한"** 쪽이다.
> 이제는 세 번째라 패턴으로 보인다 — 조건에 안 걸려서 조용히 넘어가는 코드는 직접 값을 넣어봐야 보인다.

**2. `else if` 체인은 순서가 곧 로직이다.**

위에서부터 걸리는 순간 끝이라, `age < 13` 을 `age < 18` 보다 **먼저** 써야 어린이가 걸러진다.
순서를 바꾸면 13살이 "미성년자"로 먼저 잡혀 어린이 분기는 죽은 코드가 된다.

이건 Day 4의 `canTransfer` 에서 잔액 부족 / 한도 초과 순서 문제와 **같은 이야기**다.
그때는 "메시지가 달라진다" 수준으로 봤는데, 오늘은 **분기 하나가 통째로 실행 불가능해지는** 걸 봤다.

**3. 입력값이 `NaN` 이면 모든 비교가 거짓이라, 아무 일도 안 일어난다.**

```js
var age = Number(prompt('나이를 입력하세요.'))
```

`prompt()` 가 돌려주는 건 언제나 **문자열**이라 `Number()` 로 감쌌다.
그런데 "스물"이나 빈 값을 넣으면 `NaN` 이 되고, `NaN` 은 `<` `>` `<=` `>=` **전부 거짓**이다.
마지막 분기를 `else` 가 아니라 `else if (18 <= age)` 로 써두면
`NaN` 일 때 어디에도 안 걸려서 **출력이 통째로 없다.**

`else if` 로 닫을지 `else` 로 닫을지는 취향이 아니라
**"걸리지 않는 값이 있어도 되는가"** 를 정하는 결정이었다.

### 자료형 — `bigInt` 를 채워 넣었다

원시 자료형 정리에 `bigInt` 가 빠져 있어서 보강했다.

- **`bigInt`** — 안전한 정수 범위를 넘는 정수. 숫자 뒤에 `n` 을 붙인다 (`9007199254740993n`)

JavaScript의 `number` 는 안전하게 다룰 수 있는 정수가 `9007199254740991`(2⁵³-1)까지다.
그 위로 가면 계산이 **조용히 틀린다.** 금액을 원 단위로 다루면 9천조까지라 당장 문제는 없지만,
**"정확해야 하는 큰 정수"** 라는 게 금융에서 어떤 의미인지는 기억해 둘 만하다.

> 원시 자료형 8종 — `number` `string` `boolean` `null` `undefined` `symbol` `bigInt`, 그리고 참조형 `object`.

### `alert` · `confirm` · `prompt`

브라우저가 주는 입출력 팝업 셋을 실제로 써봤다. 셋 다 **`window` 객체의 메소드**다.

| 함수 | 하는 일 | 돌려주는 값 |
| --- | --- | --- |
| `alert()` | 메시지만 띄운다 | 없음 |
| `confirm()` | 확인 / 취소 | `true` / `false` |
| `prompt()` | 값을 직접 입력받는다 | **문자열** (취소하면 `null`) |

`prompt()` 의 반환이 문자열이라는 게 핵심 3번의 출발점이다.

### 배열 — 참조 자료형의 시작

조건문을 끝내고 [`2_js_reference.js`](../01-frontend/01_web-main/03_js/2_js_reference.js) 로 넘어갔다.
배열은 **순서가 있는 집합**이고, index는 0부터, 길이는 `.length` 로 본다.

넣고 빼는 메소드는 **어느 쪽 끝이냐**로 외우면 된다.

| | 넣기 | 빼기 |
| --- | --- | --- |
| 맨 뒤 | `push()` | `pop()` |
| 맨 앞 | `unshift()` | `shift()` |
| 중간 | `splice(시작index, 삭제할개수, 삽입할값...)` | |

`splice()` 하나가 삽입·삭제·교체를 다 한다. 삭제 개수를 `0` 으로 주면 순수 삽입이고,
`1` 로 주면서 값을 넘기면 교체다. 삽입할 값은 여러 개 넘길 수 있어서
`splice(1, 1, 'bee', 'betray')` 는 **하나를 빼고 둘을 넣는다** — 배열 길이가 늘어난다.

**`sort()` 는 기본이 유니코드 정렬이라 숫자에 그냥 쓰면 안 된다.**
`[10, 9, 1]` 을 정렬하면 문자로 비교해서 `[1, 10, 9]` 가 된다.
숫자는 비교함수를 넘겨야 한다 — `sort((a, b) => a - b)`.

그런데 `NaN` · `null` · `true` · `undefined` 를 섞어놓고 돌려보니
**오름차순이 아닌 결과**가 나왔다. `a - b` 가 `NaN` 을 돌려주면 "누가 앞인지" 판정 자체가
성립하지 않아서다. (`undefined` 는 비교함수를 아예 거치지 않고 무조건 맨 뒤로 간다.)
**정렬이 조용히 틀리는 것도 오늘 세 번째 유형과 같다** — 에러가 안 난다.

> `sort()` 는 **원본을 바꾼다.** 반환값을 안 받아도 배열이 이미 정렬돼 있다.
> 그래서 결과를 볼 땐 `console.log(array2)` 로 충분하다.

**`var` 재선언을 여기서 또 밟았다.** Set 실습을 쓰면서 위에서 쓰던 `array1` 을
숫자 배열로 다시 선언했는데 **에러 없이 덮어써졌다.** Day 4에 적어둔 그 상황이 실제로 난 거라,
`array3` 으로 이름을 나눴다.

### 금융 시스템 아키텍처 — 네 개의 계(系)

계층은 **여러 서브 시스템이 모인 집합**이고, 하나의 거래가 각 계층을 거치며 처리된다.

| 구분 | 핵심 기능 | 처리 정보 | 주요 대상 |
| --- | --- | --- | --- |
| **채널계** | 고객이 만나는 접점. 요청을 받아 전달 | 거래 요청 · 인증정보 | 인터넷/스마트뱅킹 · ATM · 콜센터 |
| **계정계** | 돈이 실제로 움직이는 **원장** | 거래원장 · 계좌잔액 · 고객정보 · 계약정보 | 수신계 · 여신계 · 카드시스템 |
| **정보계** | 쌓인 데이터를 분석 | 통계 · 리스크지표 · 마케팅 데이터 | DW · 리스크관리시스템 |
| **대외계** | 외부와 데이터를 주고받는 **관문** | 대외전문 · 정산 데이터 | 금융결제원 · 카드사 · VAN/PG |

사전에 세 계로 알고 있었는데 **대외계가 하나 더 있었다.** 정보계는 계정계 데이터를 **복제해서** 분석한다.

**대외기관이 생각보다 많다** — 한국은행 · 금융결제원 · 예탁결제원 · 한국거래소 · 주택금융공사 ·
한국기업데이터 · 나이스평가정보 · VAN(펌뱅킹) 등. *금융은 혼자 돌아가지 않는다.*

**이체는 세 단계로 나뉜다 — 지급 · 청산 · 결제.**
버튼을 누르는 순간 끝나는 게 아니라, 은행 간 차액을 정산(청산)하고 최종적으로 결제되는 과정이 뒤에 있다.

**카드 결제 한 번의 흐름**은 온·오프라인이 다르다.

- **온라인** : 쇼핑몰(PG SDK로 카드정보 입력) → **PG** → **VAN** → 카드사 → 승인결과 역순 전달
- **오프라인** : 카드단말기 → **VAN** → 카드사 → 승인결과 역순 전달

| | 역할 | 예 |
| --- | --- | --- |
| **PG** (전자지급결제대행) | 온라인 쇼핑몰의 결제를 대신 처리하는 결제 플랫폼 | KG이니시스 · 토스페이먼츠 |

### 규제와 품질 — "왜 이렇게 해야 하나요"의 답

**금융IT에서 코드 품질은 취향이 아니라 규정이다.** 네 개의 법·규정이 뼈대다.

| | 무엇을 정하나 |
| --- | --- |
| **전자금융거래법** | 전자금융거래의 안전성·신뢰성. 전산장애·해킹·부정거래로부터 이용자 보호 |
| **전자금융감독규정** | 현장에서 실행하기 위한 **세부 규정** — 접근통제 · 망분리 · 프로그램 변경관리 · 백업 · 재해복구 |
| **신용정보법** | 개인신용정보의 조회 · 제공 · 보관 · 파기 · 동의 절차 |
| **개인정보보호법** | 수집·이용·제공·보관·파기와 유출 방지 안전조치 |

**실무에서 이렇게 나타난다** — 모든 배포에 승인과 기록, 화면·로그의 개인정보 마스킹,
운영 서버·DB는 사전 승인된 계정으로만 접근, 장애 시 감독기관 보고 절차, 정기 DR 점검.

**망분리** — *"편리함보다 통제 가능한 접근이 우선"*.
업무망(내부망)은 인터넷 접속 제한 · 외부매체 통제 · 소스코드와 고객정보 취급,
인터넷망은 물리적으로 분리되고 업무망으로의 자료 반입에 승인 절차가 붙는다.

> 개발 PC에서 **구글 · Stack Overflow 검색이 제한**되고, npm · pip 등 외부 패키지는
> **사내 저장소가 구축된 경우에만** 쓸 수 있다. AI 코딩 어시스턴트도 사내 구축분만 가능하다.

**개발 방법론** — 장점이 곧 단점이 되는 구조다.

| | 강점 | 약점 |
| --- | --- | --- |
| **폭포수** | 단계가 명확해 일정·예산 예측이 쉽다 | 요구 변경에 약하고 **테스트가 뒤로 몰려 결함 발견이 늦다** |
| **애자일** | 변화에 빠르게 대응, 고객이 결과를 일찍 본다 | 예측 가능성이 낮고 **산출물이 부족**해질 수 있다 |

애자일이 철학이라면 **스크럼**은 그것을 실행하는 프레임워크다 (1~4주 스프린트,
Daily Scrum 15분 이내, 핵심 역할자는 **PO**·**SM**).
금융 대형 사업은 규제·감사 대응 때문에 **폭포수가 기본형**이고, 채널·앱처럼 변화가 빠른 영역에서 애자일이 확대 중이다.

**금융권 개발 프로세스는 단계마다 산출물이 남는다.**

| 단계 | 산출물 |
| --- | --- |
| 요구사항 분석 | 요구사항 정의서(기능·비기능), 요구사항 추적표 |
| 설계 | 화면 정의서, 프로그램 정의서, 인터페이스 설계서, 테이블 정의서 |
| 개발 | 영향도 분석서, 코드 인스펙션 결과서, 소스코드 취약점 점검 |
| 테스트 | 테스트 계획서 · 시나리오 · 결과서, 성능테스트 결과서 |
| 이행·오픈 | 이행 계획서, 사용자/운영자 매뉴얼 |

**V-모델** — 왼쪽의 각 설계 단계가 오른쪽의 테스트 단계와 짝을 이룬다.
요구사항 분석↔인수 테스트, 시스템 설계↔시스템 테스트, 아키텍처 설계↔통합 테스트, 모듈 설계↔단위 테스트.

**시큐어코딩과 재해복구** — 예방과 복구를 함께 준비한다.
시큐어코딩은 행정안전부·금융보안원 가이드 기준(SQL 인젝션·XSS 방어, 입력값 검증과 출력 인코딩,
개인정보·계좌번호 마스킹, 하드코딩된 비밀번호·키 금지, 예외 처리 시 내부정보 노출 금지).
DR은 **RTO**(복구 목표 시간)와 **RPO**(복구 시점 목표 — 데이터를 몇 분까지 잃어도 되는가)로 관리하고,
주센터와 재해복구센터를 물리적으로 떨어뜨려 이중 구성하며 **정기 모의훈련**을 한다.

### 전환기의 금융IT

**클라우드** — 서비스 범위(On-Premise → **IaaS → PaaS → SaaS**)와 구성 방식
(Private · Public · Hybrid · Multi)으로 나뉜다. 다만 금융권에는 제약이 있다.

- **계정계 등 중요정보 처리 시스템**은 클라우드 운영에 제약
- 개인신용정보·고유식별정보는 **국내에서 처리·보관** 필요 (리전 선택 검토)
- 금융당국의 자료 제출 요구와 검사 협조의 어려움

**AI** — *"빠르지는 않지만 안전하게, 사람이 통제 가능한 영역부터"*.
이미 적용된 영역은 상담 챗봇(통화 후 상담 내용 요약), 내부 문서 검색(RAG),
개발 생산성 보조(코드 리뷰·테스트 코드 생성), 이상거래 탐지(FDS — 규칙 기반으로 잡기 어려운 패턴 학습).
**환각 · 폐쇄망 환경 · 최종 판단과 책임**이 남은 과제다.

### 강사가 정리한 핵심 3가지

1. **금융IT의 핵심은 신뢰성** — 거래의 정확성, 보안, 무중단 운영이 모든 설계의 출발점
2. **역할별 구조** — 채널계 · 계정계 · 정보계, 그리고 대외기관이 각자의 역할로 데이터로 연결
3. **규제는 제약이자 설계 조건** — 규제와 보안 요건을 충족하는 방식으로 설계해야 한다

### AI 시대, 개발자가 할 일

금융은 규제 때문에 AI 적용이 느린 편이었지만, 규제 완화 기조와 생성형 AI 관심 증가로
**가장 빠른 성장이 예상되는 업종**이 됐다고 했다. 사람이 하던 개발·테스트 영역을 AI가 대체하기 시작한 상황에서
개발자가 할 일로 두 가지를 들었다.

1. **모호한 요구사항을 기술 사양으로 옮기는 일** — 현업의 요청을 정확한 기술 사양과 데이터 흐름으로 정의하고,
   *"이 기능이 왜 필요한가"* 를 판단하는 주체
2. **AI가 만든 코드와 테스트를 검증하는 일** — 대량 데이터 유입, 네트워크 단절 같은
   **극단적 운영 환경의 예외 처리**는 AI가 못 잡는다. 무엇보다 **배포된 시스템의 결과와 오류에 대한
   기술적·법적 책임은 AI가 아니라 개발자**에게 있다

> 그 전제가 **"개발자가 업무 지식을 알아야 한다"** 는 것이었고, 이게 강의 전체의 주제였다.

### 왜 업무 지식이 필요한가 — 협의의 연속

**현업**은 전산 개발을 요청하는 비개발자를 통칭한다.
개발은 요청받고 끝이 아니라 **D주차부터 D+12주차까지 현업과 끊임없이 협의**하는 과정이다.

개발 요청서가 부실한 경우가 많고, **필수로 개발돼야 하는데 요청에서 빠진 항목**이 있어도
현업이 모르는 경우가 대다수라고 했다. 예로 든 개발 건은 출금과 회계처리에 걸쳐
**담당자 6명과 협의**하며 진행됐다.

**업무를 알아야 요구사항에서 빠진 걸 되물을 수 있다.** 그게 이 강의의 답이었다.

### 세 계는 물리적으로 분리돼 있다

채널계 · 계정계 · 정보계는 **각각 물리적으로 분리된 서버**에서 돈다. 그래서 이체 한 건이 이렇게 흐른다.

```
[채널계] 이체 요청
   → [계정계] 고객계좌 잔액 확인 · 출금 요청 금액 확인
   → 조건 만족 시 출금
   → [채널계] 이체 응답
   → [정보계] 이체 이력 원장 적재 및 DW 전송
```

**응답을 먼저 돌려주고 정보계 적재는 뒤따른다.** ① 에서 배운 *"정보계는 복제해서 쓴다"* 가
여기서 실행 순서로 보였다.

### 계층 사이는 무엇으로 통신하는가 — MCA · EAI · FEP

서버가 분리돼 있으니 **연결 방식**이 필요하다. 셋을 구분하는 기준이 명확했다.

| | 뜻 | 언제 쓰나 |
| --- | --- | --- |
| **MCA** | Multi Channel Architecture | **같은 기관 안**에서 서버만 다른 시스템 영역 간 통신 (채널계 ↔ 계정계) |
| **FEP** | Front End Processor | **다른 기관**의 시스템과 통신 (금융결제원 · 금융감독원 · NICE · KCB 등) |
| **EAI** | Enterprise Application Integration | 시스템 간 연계, **파일 단위 전송(File to File)** 등 |

**같은 기관인데도 FEP 를 쓰는 경우가 있다.** 법률적 사유로 **대외 망에 준하는 보안·망분리 통제**를
적용해야 하거나, 내부에서도 **보안등급이 다른 망 사이를 연동**할 때다.
*"기관이 다르냐"가 아니라 "보안 경계를 넘느냐"가 진짜 기준*이었다.

MCA 는 채널계의 입력(source)을 계정계가 알아듣는 형식(target)으로 **데이터 매핑**하고,
응답은 그 반대로 매핑해 돌려준다. **계층이 다르면 데이터 형식도 다르다**는 뜻이다.

### 계정계의 두 단어 — 원장과 센터컷

**원장(元帳)** 은 컴퓨터가 없던 수기 장부 시절에서 왔다. 각 영업점·창구가 입출금을 일차로 기록하고,
메인 장부에 집계해 **최종 잔액을 확정한 장부**가 원장이다. 수십 년 쓰던 용어를 전산에 그대로 가져왔다.

**센터컷(Center Cut)** 은 **중앙 일괄 집중 처리 방식**이다.
결제대금 출금 의뢰, 포인트 페이백 입금 의뢰 같은 요청을 실시간으로 처리하지 않고
**가용 시간 내에 우선순위와 부하를 보며 순차 수행**한다.

> **왜 실시간이 아닌가** — 수천 건을 동시에 실시간 처리하면 **서버 과부하로 다운될 확률이 올라간다.**
> 센터컷은 **시스템 안정성(과부하 방지)과 정합성 확보**를 위한 수단이다.

**"빠른 게 항상 좋은 게 아니다"** 가 여기서 나왔다. 일부러 모아서 순차로 돌린다.

### 대량 배치를 어떻게 다루는가

계정계 배치의 두 가지 기법이 인상적이었다.

**1) 분할 병렬 처리** — 자동이체 대상 파일 하나에 **몇백만 건**이 들어온다.
한 번에 처리하는 것보다 **다수 파일로 분할해 병렬 처리**하는 쪽이 빠르다.

**2) 커밋 단위와 재수행** — *"300만 건 중 290만 건 처리 후 에러가 나면?"* 이라는 질문이 나왔다.

```
10,000건을 1,000건 단위로 처리
  1,000건마다 DB commit → commitCnt + 1
  9,800번째에서 에러 발생 → commitCnt(9)를 보고 9번 구간부터 재수행
```

**어디까지 성공했는지를 기록해두면 처음부터 다시 안 해도 된다.**
오전에 배운 반복문이 "몇 번 도느냐"였다면, 여기서는 **"중간에 죽으면 어디서 다시 시작하느냐"** 였다.

**3) 선행 작업 조건** — 파일 기반 EAI 연계에서, 앞 배치가 파일을 만들고 뒤 배치가 그 파일을 가져가는 구조다.
**파일이 없으면 후행 작업이 통째로 실패**한다. 그래서 **선행 작업 조건을 걸어두고,
정상 수행되지 않으면 후행 작업을 아예 시작하지 않게** 한다.

> 이것도 결국 **조건문**이다. "있으면 진행, 없으면 중단." 오전에 짠 `if` 와 구조가 같은데
> 걸린 게 몇백만 건짜리 자금 처리라는 점만 다르다.

### 각 계에서 일한다는 것 — 강사의 현장 이야기

가장 도움이 된 부분이었다. **같은 회사 안에서도 어느 계에 있느냐로 일의 성격이 완전히 달랐다.**

**채널계**
- 마케팅 · 법적 제도 시행 · 내부 정책 변경 · 신상품 출시로 **신규·변경 개발 건이 많다**
- 잘못 적용하면 **수많은 영업점과 고객센터에서 전화(민원)** 가 온다
- 금융권에 따라 개발 툴이 다양하고, **순수 HTML·CSS·JS 로 개발하는 경우도 많다** (퍼블리셔가 없는 경우도)
- 최근에는 **하이브리드 웹** 추세가 강해 네이티브 개발자 수요가 줄어드는 흐름

**계정계**
- **속도보다 안정성과 정합성이 1순위**
- 입출금 · 계좌이체 · 대출실행 · 이자계산 등 **돈과 직결된 핵심 로직**. 잘못 적용하면 **금전적 대량 손실**
- **배치 에러가 나면 새벽이든 주말이든 즉시 출근**하는 상황이 빈번
- 정확한 업무·회계 지식이 필요하고, 특히 **금융기관 입장에서 생각**해야 한다
  → **고객의 자산은 은행의 부채다** (예금)
- 대량 데이터 처리와 중단 시 복구를 어떻게 할지 늘 생각해야 한다

**정보계**
- 대내외 보고서, 경영평가 실적 산출
- 대부분 **확정된 원장(일·월 스냅샷) 기준**으로 작업한다. 실시간 원장이 아니다
- **평가 시즌(상·하반기)** 에 영업점 연락이 몰린다
- 한국은행 · 금융감독원 등 **대외기관 보고서**는 특히 유의
- SQL 위주로 개발하다 보니 **프론트·백엔드 능력이 퇴보하는 것에 대한 고민**이 있다

> **"고객의 자산은 은행의 부채"** 가 오늘 제일 크게 남았다.
> 예금을 자산으로만 보던 시각이 뒤집혔다. 대고객 화면만 보면 절대 안 보이는 관점이다.

**대외계 이야기는 없었다.** ① 에서 네 번째 계로 배웠고 이 강의에서도 FEP 통신 대상
(금융감독원 · 금융결제원 · NICE · KCB)과 카드의 VAN 연계로 계속 나왔는데,
**"거기서 일한다는 것"** 만 빠졌다. 두 강의 모두 대외계를 **구조로는 다뤘지만 직무로는 안 다뤘다.**

**확인할 것** — 대외계 개발은 다른 세 계와 무엇이 다른가.
외부 기관과 규격(전문)을 맞춰야 하니 **내 일정만으로 배포를 못 정할 것 같은데**, 실제로 어떤가.

신뢰성이 최우선인 곳이니 **규격을 자발적으로 바꿀 일은 거의 없을 것 같다.**
그런데 강의 안에 반례가 있었다 — 채널계에 **"법적 제도 시행"** 으로 변경 개발 건이 많다고 했고,
발전사에는 **오픈뱅킹(2019, 표준 오픈API)** 과 **마이데이터** 가 있었다.
개별 금융사가 "우리는 안 바꾸겠다"를 할 수 있는 종류가 아니다.

정리하면 **"안 바꾼다"가 아니라 "스스로는 안 바꾸는데, 밖에서 바꾸라고 하면 일정까지 밖에서 온다"** 에 가깝다.
자발적 변경을 극도로 억제하는 조직일수록 **외부발 변경이 왔을 때 부담이 클 것 같은데**, 실제로 어떻게 감당하는가.

### 카드 프로세스 맛보기

카드는 **매출 → 매입 → 청구 → 입금(회수)** 순으로 흐른다.

**매출**은 거래가 발생한 시점의 기록이다.
*A고객이 B편의점에서 1만원 과자를 사면* → `날짜 · 고객 · 가맹점 · 금액` 의 매출 건이 생기고,
**추후 고객별 결제금액 청구에 쓰인다.**

**카드 상품 세 가지**

| | 내용 |
| --- | --- |
| **일반신용판매** | 이용대금을 일시에 결제 |
| **할부신용판매** | 5만원 이상을 할부기간 내 월 단위로 분할 결제 (+ 할부수수료) |
| **단기카드대출** | 신용카드로 받는 현금서비스 |

그 위에 **카드 상품 고유의 서비스**(청구할인 · 포인트 적립 등)가 적용된다.

**청구 작업 뒤 고객에게 결제금액을 청구하고 입금(회수)** 하는데,
**입금이 제대로 안 되면 다음날 연체 고객으로 잡힌다.**

> **"할부수수료 계산식은 외울 필요 없다. 각 카드 프로세스별로 하는 업무와 역할을 기억하라"** 고 했다.
> 공식이 아니라 **흐름의 어느 지점인지**를 알라는 뜻으로 들렸다.

## 강의 전 질문에 대한 답

**세 계(系)가 실제로 어떻게 연결되는가**
채널계가 요청을 받아 계정계로 넘기고, 계정계가 원장을 처리한다. 정보계는 계정계 데이터를
**복제해서** 분석하므로 거래 경로에 직접 끼지 않는다. 은행 밖으로 나가는 건 **대외계**가 맡는다.
이체는 그 위에서 **지급 · 청산 · 결제** 세 단계로 다시 나뉜다.

**Day 2·3에서 만든 화면이 뒤쪽 시스템과 어디서 만나는가**
내가 만든 건 **채널계**다. 채널계는 거래 요청과 인증정보까지만 다루고,
**잔액과 원장은 계정계**가 갖는다. 화면에서 `.value` 로 꺼낸 값이 그대로 돈을 움직이는 게 아니라,
계정계에 요청을 넘기는 입구였던 셈이다.

**카드 개발이 은행 계좌 개발과 다른 지점**
카드는 **승인은 실시간, 정산은 배치**로 나뉘고 **VAN·가맹점 등 외부 연계**가 필수다.
그래서 **지연이 곧 손실**이다. 은행은 거래량이 가장 많고 안정성이 최우선이다.
상세는 이어진 ② 세션에서 다뤘다.
